# ThinCoder VS Code — 三观与定位

> 本文档定义 VS Code 扩展的设计哲学。与 ThinCoder 共享三观基础（世界观/人生观/价值观），本文档只补充 VS Code 场景特有的部分。

---

## VS Code 场景特有的世界观

### 1. Agent 活在编辑器里

Agent 不是终端里的"独立进程"——它和用户共享同一个编辑器窗口。用户正在看的文件、光标位置、最近编辑记录，都是 Agent 的上下文。

这意味着 Agent 应该像同事坐在旁边看屏幕一样自然：看到用户刚改了什么东西，不用等用户开口就应该能接上话。

（当前实现：受限于 VS Code API 暴露程度，尚未实现编辑器上下文感知，仅通过 workspace 文件夹获取项目范围。）

### 2. 文件操作是"自然动作"

在 CLI 中，`write` 一个文件只是一个系统调用。在 VS Code 中，`write` 应该在编辑器中打开文件——让用户看到变化。不是"Agent 悄悄改了文件"，而是"Agent 改了文件并展示给你看"。

这是编辑器场景的 UX 基础：可见性即信任。Agent 的所有文件修改都应该是透明的、可审查的、可撤销的（通过编辑器 undo 或 git）。

（当前实现：`write` 和 `edit` 工具执行后自动调用 `workspace.openTextDocument` + `window.showTextDocument`。）

### 3. 会话 = 项目上下文

CLI 会话是终端窗口的生命周期（启动 → 退出）。VS Code 会话是 workspace 的生命周期（打开项目 → 关闭项目）。Agent 的会话应该跟着 workspace 走——打开同一个项目，历史对话还在。切换到不同项目，对话重新开始。

这不是技术限制，而是设计选择：对话历史的意义在于它所处的项目上下文。在项目 A 中讨论"重构认证模块"的记录，放在项目 B 中毫无意义。

## VS Code 场景特有的人生观

### 1. Agent 是编辑器的"技术副驾驶"

用户的首要身份是编辑器的使用者——写代码、调试、读文档、做 code review。Agent 是这个工作流中的一个加速器：

- 用户卡住了 → Agent 能解释代码
- 用户想加功能 → Agent 能实现
- 用户不确定怎么设计 → Agent 能出方案
- 用户刚改了代码不放心 → Agent 能跑测试验证

Agent 不替代用户的工作流，而是融入它。

### 2. 该安静时安静，该出声时出声

VS Code 是一个多任务环境——用户可能在编译、调试、切文件、看 diff。Agent 不应该在每个操作后都弹通知打断用户。通知仅用于：

- 配置问题（如缺少 API key）
- 首次完成（如 setup 成功）
- 致命错误（如 agent 崩溃）

常规的 agent 行为——开始工作、产生输出、完成任务——都应该只在聊天面板内可见，不弹出系统通知。

（当前实现：`showInformationMessage` 仅用于 setup 和配置保存；agent 运行过程中的所有输出通过 webview 传递。）

## VS Code 场景特有的价值观

### 1. 可见性 > 自动化

在编辑器环境中，用户对代码的"所有权"感更强——这是"我的代码"。Agent 修改代码时，必须让用户看到：

- **改了什么**（文件内容变化在编辑器标签页中可见）
- **为什么改**（agent 的回复解释原因）
- **怎么撤销**（git diff 可用，编辑器 undo 可用）

比起 CLI 的"批量执行 + 事后 review"模式，VS Code 场景应该更偏向"逐文件可见"。

### 2. 环境感知优先于工具能力

一个有环境感知的 Agent 比一个有 50 个工具的 Agent 更有用。VS Code 已经收集了大量上下文——当前打开的文件、git 状态、语言服务器信息、调试器状态、最近编辑——把这些喂给 Agent，比给它多加 20 个工具意义更大。

工具是 Agent 的手，上下文是 Agent 的眼睛。先擦亮眼睛，再增加手臂。

（当前实现：环境感知较基础——仅有 workspace 文件夹路径、文件系统。编辑器状态感知为待做事项。）

### 3. 性能不打扰编辑器

VS Code 扩展运行在 Extension Host 进程中，与编辑器的响应性共享同一个 Node.js 线程。Agent 的任何同步阻塞操作都会直接导致编辑器卡顿。

- 文件扫描（repo outline）应该用异步 + 流式，不阻塞事件循环
- LLM 请求自然是异步的（fetch）
- bash 工具执行使用子进程，不阻塞主线程

## 与 CLI 的定位差异

| 维度 | CLI 产品 | VS Code 产品 |
|------|----------|-------------|
|------|-------------------|-------------------|
| 定位 | 独立开发工作站 | 编辑器内的技术副驾驶 |
| 使用场景 | 无 GUI 环境、远程服务器、CI | 日常编码、review、调试 |
| 交互模式 | 聊天式，Agent 主导节奏 | 混合式，用户和 Agent 交替 |
| 信任模型 | 终端内"全权委托" | 编辑器内"可见即信任" |
| 功能深度 | 全功能（记忆/MCP/checkpoint） | 核心 agent + 编辑器集成 |
| 演进策略 | 功能试验田 | 稳定体验，跟随后端 |

CLI 是"我信任 Agent，让它帮我完成整个任务"。VS Code 是"我在写代码，Agent 在旁边帮我"。前者适合批处理式的大型任务，后者适合交互式的小步快跑。
